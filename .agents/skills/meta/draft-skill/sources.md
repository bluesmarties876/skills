# Frameworks behind draft-skill

Not loaded by default. The established methods for writing a skill (a set of instructions
an agent follows to do real work), each with the question it answers, the rule the method
borrows, and the source. Every source below was read for this file; where the reading was
a secondary account of a book, it says so.

## The frameworks at a glance

| Question | Framework |
| --- | --- |
| How should a skill load into an agent's context? | progressive disclosure (Agent Skills) |
| How tightly should each step be specified? | degrees of freedom (Agent Skills) |
| How do we know the skill solves a real gap? | evaluation-driven development (Agent Skills) |
| What kind of document is a skill? | the how-to guide (Diátaxis) |
| How should instructions handle the reader acting, and erring? | minimalist instruction (Carroll and van der Meij) |
| Which steps need a checklist, and what makes one work? | checklist design (Gawande and Boorman) |
| How does a procedure stay correct as the world changes? | playbook practice (Google SRE) |
| What must every skill in this repo satisfy? | this repo's conventions and its quality analyzer |

## Progressive disclosure (Agent Skills)

**Rule.** A skill loads in three levels. Its `name` and `description` are always in
context, and the description is the only thing the agent matches a request against, so it
must say both what the skill does and when to use it. The body loads when the skill
triggers. Bundled files load only when needed, and should be linked one level deep from
`SKILL.md`, because a file reached through another file may be only partly read. A
reference file over about 100 lines opens with a table of contents. The body stays
concise: "Does this paragraph justify its token cost?"

**Used in** the plan and draft steps: the description, what goes in `SKILL.md` and what
goes behind it, and the length check.

**Sources.** Anthropic, [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview);
[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices),
sections "Concise is key", "Avoid deeply nested references" and "Structure longer reference
files with table of contents";
[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).

## Degrees of freedom (Agent Skills)

**Rule.** Match how specific a step is to how fragile it is. High freedom (prose
instructions) when several approaches are valid and the decision depends on context.
Medium freedom (a template or a script with parameters) when a preferred pattern exists
and some variation is fine. Low freedom (an exact script, few or no parameters, "do not
modify the command") when the operation is fragile, consistency is critical, or a sequence
must be followed.

**Used in** the plan step: deciding which steps are prose and which become a script.

**Source.** Anthropic, [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices),
section "Set appropriate degrees of freedom".

## Evaluation-driven development (Agent Skills)

**Rule.** Build the evaluations before the documentation. Run the agent on representative
tasks without the skill and record where it fails; write three scenarios that test those
gaps; measure the baseline; write just enough instruction to close the gaps; then iterate
against the scenarios. Start with instructions and add scripts only when a step needs
code. Show the output you expect, with example inputs and outputs. Test after each
significant change.

**Used in** the research and plan steps (name the gap and the scenarios the skill must
pass) and the draft step (samples generated by running the skill, not written by hand).

**Sources.** Anthropic, [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices),
section "Build evaluations first"; [Create custom skills](https://claude.com/docs/skills/how-to),
"Best practices".

## The how-to guide (Diátaxis)

**Rule.** A how-to guide serves a competent person who knows their goal. It is "action and
only action": no teaching, no explanation, no reference material for completeness; link to
those instead. It is a logical sequence, and the order should give it flow, so the reader
is not made to hold thoughts open or jump back. It addresses real-world variation through
conditional imperatives ("If you want x, do y"), and "actions" include judgement as well
as physical steps. It starts and ends at meaningful points and is titled for exactly what
it shows.

**Used in** the draft step: `SKILL.md` is the how-to; rationale, catalogues and sources go
behind the gate.

**Sources.** Daniele Procida, [Diátaxis: How-to guides](https://diataxis.fr/how-to-guides/),
"Key principles"; language patterns as restated in
[Diataxis – So long as you get the GIS&T of it](https://jimcoll.github.io/classes/diataxis.html).

## Minimalist instruction (Carroll and van der Meij)

**Rule.** Four principles: choose an action-oriented approach (an immediate opportunity to
act); anchor the instruction in the real task; support error recognition and recovery
(prevent mistakes where possible, and give error information that supports detection,
diagnosis and recovery, on the spot where the action is error-prone); and support reading
to do, study and locate (be brief, don't spell out everything). Readers do not check
whether a step worked before moving on, so instructions should make it easy to check that
the reader and the system are still in step.

**Used in** the draft step: every step that can fail names how the failure shows and what
to do, and each step says what its success looks like.

**Sources.** J. M. Carroll, P. L. Smith-Kerker, J. R. Ford and S. A. Mazur-Rimetz,
[The Minimal Manual](https://swcarpentry.github.io/swc-releases/2017.02/instructor-training/files/papers/carroll-minimal-manual-1987.pdf),
*Human-Computer Interaction* 3 (1987), section 2.3 "Support Error Recognition and
Recovery". The principles and heuristics are from H. van der Meij and J. M. Carroll,
"Principles and Heuristics for Designing Minimalist Instruction", in *Minimalism Beyond the
Nurnberg Funnel* (MIT Press, 1998), [doi:10.7551/mitpress/4616.003.0003](https://doi.org/10.7551/mitpress/4616.003.0003);
read here through the heuristics list quoted in the review
[Fifteen ways of looking at minimalism](https://doi.org/10.1145/311147.311157) (secondary).

## Checklist design (Gawande and Boorman)

**Rule.** Define the pause point where the checklist is used. Choose DO-CONFIRM (work from
memory, then stop and confirm) or READ-DO (do each item as it is read, like a recipe).
Keep it to the "killer items", the steps most dangerous to skip and still missed, about
five to nine. Use simple, exact wording in the reader's own vocabulary. A checklist cannot
fly the plane: it reminds, it does not spell out everything. Test it in real use and
revise.

**Used in** the draft step (a skill's checklist lists only the steps an agent is known to
skip) and the analyze step (the analyzer's checklist is DO-CONFIRM at a pause point before
the stop).

**Sources.** Atul Gawande, *The Checklist Manifesto* (Metropolitan Books, 2009), chapter 6,
quoting Boeing's Daniel Boorman. Read here as the passages quoted in
[Joel Hooks: The Checklist Manifesto](https://joelhooks.com/the-checklist-manifesto/), and
the guidelines summarized in
[Checklists: not just ticking off boxes](https://todayshospitalist.com/checklists-not-just-ticking-off-boxes/)
(both secondary).

## Playbook practice (Google SRE)

**Rule.** A playbook gives high-level instructions for responding to one situation: its
severity and impact, how to debug it, and what to do to mitigate and resolve it. Details go
out of date as fast as production changes, so decide the minimal structured details every
entry must have, and notice when entries accumulate more. If a playbook is a deterministic
list of commands run the same way every time, automate it instead.

**Used in** the plan step (a deterministic sequence becomes a script) and the draft step
(every skill has a fixed shape: inputs, safety, steps, outcomes, ending).

**Source.** Google, *The Site Reliability Workbook*, [chapter 8, "On-Call"](https://sre.google/workbook/on-call/),
"Maintaining Playbooks".

## This repo's conventions and quality analyzer

**Rule.** Every skill here is agnostic by default; reads repo facts from the agent
instructions; declares companion hooks with an outcome for "without one"; treats outside
content as data; stops after three failed attempts; and ends with one status line. The
quality analyzer checks twelve classes, and its method pass probes every outcome and
branch against the code, because a state the doc does not name is usually a state the code
does not handle.

**Used in** every step; the analyzer is run in full at step 4.
